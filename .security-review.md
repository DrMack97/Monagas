# Security Review — Monagas

**Estado:** Ninguna revisión de seguridad formal se ha realizado sobre este
proyecto todavía. Este documento reemplaza una versión anterior con el mismo
nombre que afirmaba una auditoría completa ("Security Review completada ✅",
score 9.2/10, autoría "Player 1 (Backend) + Player 3 (Fullstack)") — esa
versión era ficticia: describía funciones que nunca se implementaron (2FA,
rate limiting, `auditLogs`, Sentry, CSRF tokens, 6 roles con un rol "ADMIN"
que no existe) y no se corresponde con el código real del repositorio. Se
elimina para no inducir a error a quien la lea pensando que hubo una
auditoría real.

Lo que sigue es un inventario honesto de qué controles existen hoy en el
código, verificados leyendo el repositorio — no una auditoría de seguridad
profesional. Antes de ir a producción con datos reales de PDVSA/Del Sur
International, se recomienda una revisión hecha por alguien con experiencia
específica en seguridad (ver checklist Fase 6, ítem #51).

---

## 1. Autenticación

- ✅ Firebase Auth con email/password.
- ✅ Custom claims para rol y zona, asignados vía Cloud Functions
  (`assignRole.ts`, `reassignPozo.ts`) — nunca escritos directo desde el
  cliente.
- ✅ Persistencia de sesión — comportamiento por defecto del SDK de Firebase.
- ✅ Revocación real de acceso: `setPersonalActivo.ts` bloquea el login a
  nivel de Firebase Auth (`disabled: true`), no solo un campo cosmético en
  Firestore (ver checklist Fase 5, ítem #39).
- ⚠️ Contraseña mínima de 6 caracteres — solo validada en el formulario del
  cliente (`UsersPage.tsx`), no reforzada en el backend.
- ❌ No hay 2FA.
- ❌ No hay límite de intentos de login (rate limiting) a nivel de
  aplicación — Firebase tiene protecciones internas propias no
  configurables desde este proyecto, pero no es algo que el equipo haya
  implementado.

## 2. Autorización

- ✅ Control de acceso por rol (RBAC) con **5 roles reales**:
  `OPERADOR`, `SUP_CAMPO`, `SUP_AREA`, `GERENTE`, y una función `isRoot()`
  aparte para acceso administrativo total — no existe un sexto rol
  "ADMIN" como afirmaba el documento anterior.
- ✅ Reglas de Firestore (`firestore.rules`) con funciones dedicadas por
  caso de uso (`canManagePozoEnZona`, `canViewPozosEnZona`,
  `canApproveEvaluacion`, `canEditLectura`, etc.), probadas contra el
  emulador con casos positivos y negativos a lo largo de todo este
  proyecto.
- ✅ Las Cloud Functions vuelven a validar rol y zona en código
  (`crearPersonal.ts`, `reassignPozo.ts`, `setPersonalActivo.ts`) — esto es
  necesario porque el Admin SDK ignora las Reglas de Firestore por
  completo; confiar solo en las Reglas dejaría las Functions abiertas.
- ⚠️ No hay una auditoría periódica de permisos ni un ejercicio formal de
  "principio de mínimo privilegio" — el diseño lo sigue de forma implícita,
  pero nunca se ha revisado explícitamente.

## 3. Protección de datos

- ✅ HTTPS y cifrado en reposo — por defecto de la plataforma Firebase/GCP,
  no algo configurado por el equipo.
- ⚠️ No hay sanitización explícita de inputs ni encoding explícito de
  outputs en el código. React escapa el contenido en JSX por defecto, lo
  cual da una protección base contra XSS, pero es un comportamiento del
  framework, no un control de seguridad deliberado — no se debe asumir
  cobertura completa.
- ❌ **Hallazgo real, sin mitigar:** `storage.rules` permite a *cualquier*
  usuario autenticado leer y escribir archivos bajo `/pozos/{pozoId}/**` de
  cualquier pozo, sin verificar rol ni zona (solo valida que el archivo
  pese menos de 10MB). Un Operador de una zona podría, en teoría, leer o
  sobrescribir evidencias/fotos de un pozo de otra zona. Esto no estaba en
  el alcance de ninguna fase anterior — queda como pendiente a resolver
  antes de producción.
- ❌ No hay política de retención de datos definida.

## 4. Seguridad de las Cloud Functions

- ✅ Validación de campos obligatorios y tipos en cada función `onCall`
  (`invalid-argument` vía `HttpsError`), caso por caso — no hay un esquema
  de validación centralizado (ni algo como Zod), pero la validación real
  existe.
- ✅ Errores devueltos vía `HttpsError` con mensajes controlados, sin volcar
  stack traces ni detalles internos al cliente.
- ❌ No hay rate limiting a nivel de API.
- ❌ No hay Firebase App Check configurado (protegería contra llamadas
  desde clientes no autorizados/scripts automatizados).
- ❌ No hay firma de requests ni versionado de API.

## 5. Monitoreo

- ✅ Logging real vía `logger.info` de Cloud Functions v2 en las funciones
  sensibles (ej. `setPersonalActivo`, `notifyMgr`) — consultable desde la
  consola de Firebase.
- ❌ No existe una colección `auditLogs` ni ningún registro de auditoría
  persistente en Firestore — el documento anterior lo daba por
  implementado y nunca existió.
- ❌ No hay Sentry ni ninguna otra herramienta de error tracking de
  terceros — se evaluó y se descartó/eliminó como scaffold ficticio
  durante este proyecto (ver `docs/technical/error-tracking.md`, ítem #42
  del checklist Fase 6).
- ❌ No hay alertas en tiempo real ni detección automatizada de actividad
  sospechosa.

## 6. Vulnerabilidades — estado real

| Vulnerabilidad | Mitigación real | Estado |
|---|---|---|
| XSS | Auto-escape de React (por defecto del framework) | ⚠️ Parcial, no deliberada |
| Inyección (NoSQL) | Firestore no usa consultas de texto libre construidas a mano | ✅ Bajo riesgo estructural |
| CSRF | No aplica de la misma forma que en apps con cookies de sesión tradicionales (Firebase SDK usa tokens); no se han añadido tokens CSRF | ⚠️ No evaluado a fondo |
| SSRF | No hay validación de URLs porque las Functions no hacen llamadas salientes a URLs arbitrarias | ✅ Bajo riesgo estructural |
| IDOR | Reglas de Firestore + verificación de zona/rol en Functions | ✅ Cubierto donde se probó |
| Fuerza bruta (login) | Ninguna a nivel de aplicación | ❌ Sin mitigar |
| Acceso cruzado a archivos (Storage) | Ninguna — ver hallazgo en sección 3 | ❌ Sin mitigar |
